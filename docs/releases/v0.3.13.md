# v0.3.13 candidate — private Homebrew runtime

**Status: not ready for stable promotion.** The public formula still points
at the existing v0.3.12 archive and checksum.

## Distribution

The generated candidate formula selects one checksum-locked resource for
the host and stages `opencode`, its license and manifest under
`libexec/runtime/`.
Only `opencode-team` is linked into the public `bin`. BEST and FREE use that
one executable, never the caller's `opencode`. Packaged mode rejects
overrides, missing resources, wrong platform/revision, an unexpected version
or changed bytes instead of falling back. A marker outside the runtime
directory applies this protection to both installed launcher entrypoints.
The published v0.3.12 formula and Homebrew dependencies are unchanged.
Installing the Team resource does not compile it or invoke Bun or Python.
Homebrew itself may still require working developer tools to install a
formula, and missing dependency bottles can trigger source builds.

The launcher adds the shipped Guard plugin to the native server's inline
config for each isolated profile. Guard itself does not change config files.
Session Guard protects the **full TUI composer**, including queue submission, and
only detects conflicts supported by explicit evidence. Mini, ACP, direct
API/CLI prompts, web and desktop are not protected.

## Upgrade and cleanup

New packaged BEST configurations use Homebrew's `opt` path for Governor
and Team skills. On launch the candidate backs up and rewrites only matching
versioned paths from its own Cellar rack, including paths whose old keg
has already been removed. JSONC comments and unrelated settings are
preserved. FREE has no such references in its generated config. The
executable and Guard come from the same installed Team keg, not from `PATH`.

`brew cleanup` is not a live-process migration. Upgrade with
`HOMEBREW_NO_INSTALL_CLEANUP=1` if any Team process is still using the old
installation. Let those processes exit normally and defer cleanup until
then; do not kill them or remove their keg while they are active. Team
does not run cleanup or track live users of old kegs.

## Build and release gates

`.github/scripts/build-team-runtime.sh` verifies the exact upstream
`c0ad18b402eb2827fc1ee71c171b1177b3fc02d1` archive SHA-256 before applying
the versioned patch. It uses Bun 1.4.4, the upstream frozen dependency lock
and the full upstream CLI/web build (no `--skip-web-ui`). Tar/gzip metadata
is normalized. The release matrix pins Node and Bun; publish only known
artifact bytes that passed qualification, never another rebuild under an
already approved digest. Two pinned arm64 builds produced identical web
archives and equal-length executables (234,399,458 bytes). The native Mach-O
text/data segments and the pre-signature portion of `__LINKEDIT` matched.
The differences are in the Bun payload (`__BUN,__bun`, first difference
at zero-based offset 97,297,444) and its dependent Mach-O signature. The
bundled code embeds the absolute source directory; changing it affected
20 hashed chunk names and 22 module bytecode payloads. After mapping
the renamed chunks and the source directory, no differences remained
in the bundled JavaScript. All changed signature slots matched the hashes
of changed payload pages. Tar/gzip metadata and signing alone are not the
cause; changing the source directory also changed the output with bytecode
disabled in a diagnostic build.

Two fresh source copies staged at the **same absolute path**, with bytecode
enabled, the same saved web archive, and different output directories,
produced identical arm64 executables (`8d3fb775f6f13b0161c7ea543586fb229a44609b8a653b265b18073536d6f487`).
For a future controlled rebuild, use the same absolute staging path on a
disposable builder; the existing script accepts that directory as its
output argument and extracts the source into its `source/` subdirectory.
Move the first build aside before running the second at that path. No
toolchain change is needed for this mitigation. End-to-end and cross-host
binary reproducibility are **not** established. The upstream build and
qualified bytes are unchanged; the pins, artifact lock, installed digest
and run-bound qualification check specific bytes, not future rebuilds.

The dispatch-only runtime workflow builds, installs and tests the candidate
without publishing a release. The existing Phase A and B gates select
artifacts from a successful matrix for the exact source commit. Phase A
binds that matrix run and lock digest to the handoff, and Phase B checks
the same receipt and runtime bytes. A stable
formula is generated with `render-staging-formula.rb --runtime` only from
all four reviewed runtime locks and the official source archive checksum.
Without a local directory the generated formula points at the versioned
release assets; passing a local directory instead verifies the actual
compressed files and emits `file://` URLs for staging. The assets must be
made available under the versioned URLs **before** pointing the stable tap
at that formula. Asset publication and stable promotion are separate future
operations; no implicit upload or publication is part of this candidate.

For a local handoff, keep the runtime archive directory and its
`runtime-lock.json` together and pass the directory as the last argument
to `render-staging-formula.rb --handoff`. The verifier checks the same
formula that will be installed, the source archive digest, the runtime
lock and the referenced resource files. Do not use the stable tap for the
unpublished candidate.

The Linux installs used standard-prefix Homebrew in Ubuntu 24.04 with
glibc 2.39 and bottled dependencies. Both selected the expected ELF
and manifest digest; neither linked `opencode` publicly. The prior
network-isolated TUI A–G results still apply to the unchanged binaries.

On macOS arm64, `brew install --ignore-dependencies` upgraded the existing
keg, and explicit `brew cleanup` removed 0.3.12. BEST and FREE then
reopened their native fixture sessions; Governor was active and the Team
skill was discovered via `opt`. Only the two managed config paths changed;
fixture CLI preferences, auth and checkpoint files matched their original
checksums. Rollback reinstalled 0.3.12 and reopened the same sessions. The
separate standard OpenCode executable was byte-identical. Full dependency
resolution in the nonstandard prefix previously timed out rebuilding
gettext; it was not bypassed in the Linux runs.

Stable promotion remains blocked on a successful Intel Homebrew install
and the standard-prefix release matrix. Emulation and the untested live
editor-selection change are limits of the evidence. Non-identical rebuilds
rule out claiming binary reproducibility; promotion must use the exact
qualified artifact bytes, not a substitute rebuild.

Each upstream update requires review/rebase of the pre-submit patch,
updating the source/version and patch pins, rebuilding all four artifacts,
and rechecking the full composer (especially queue/revert), clean install,
upgrade and rollback. Do not float to the latest OpenCode version or reuse
old checksums. There is one runtime download per host, not one per profile.

## Rollback

Before a future upgrade, retain the trusted v0.3.12 formula and checksum or
keep its keg with `HOMEBREW_NO_INSTALL_CLEANUP=1`. Close the Team TUIs normally.
In the target tap restore the trusted v0.3.12 formula, remove only the v0.3.13
Team keg, then link the retained v0.3.12 keg (`brew link opencode-team`);
if it is no longer present, reinstall from the pinned old formula instead.
Verify `opencode-team version` and the version of the separate standard
OpenCode. No profile setup, config rollback or session deletion is required
to switch the keg. As with any native runtime change, take a profile backup
before starting against a different OpenCode database version; switching
kegs does not reverse database migrations. Use the same Homebrew formula
name and prefix for rollback, so Homebrew points the persisted `opt`
references at the restored keg.
